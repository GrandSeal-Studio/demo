    12.2 本轮 Demo 的范围
    - 现在实现可操作 Demo，不只是菜单草图。NLH，2～6 名模拟玩家，盲注 0.50/1.00，初始每人 100.00 模拟筹码，抽水 5% 封顶 3.00，未见翻牌不抽水。 - 一名荷官同一时刻只绑定一桌；当前 Demo 的本机沙箱只运行一张桌，LIVE-01／LIVE-02 二选一。不同荷官账号不能操作已被占用的桌。 - 荷官手工录入每位玩家两张底牌与公共牌；选择花色点数，不自动代抽。底牌确认后荷官概览遮罩；手机模拟区只呈现当前行动玩家本人底牌。实体底牌的受控读取方式（摄像或指定录入工位）须在正式接现场前确认。 - 玩家通过手机发起行动，荷官只确认收到的行动，不允许改金额、代下注或补填“玩家想做的行动”。Demo 通过独立“玩家手机模拟区”产生事件，明确标模拟。 - 系统自动计算比牌、主池边池、未跟注退回、平分及尾差、抽水；荷官核对后确认一次。未确认不派发胜出筹码；不得手输赢家或改派奖金额。 - 独立本地存储 `dz_live_dealer_v1`；不修改 WAP 钱包、牌桌、手机计时或实际资金。总后台可只读获取这个沙箱的已结算／已终止记录和异常报告。 - 两步验证示范账号 `dealer_01`／`dealer_02`，示范密码 123456、验证码 000000。主管模拟身份仅为演示开关，正式版必须独立账号、权限、会话，不能保留自由切换身份入口。 - 本轮不实现真实视频上传、真实手机 WS、现场设备识别、多人跨服务器锁、真人赛事、Jackpot、兑现、多次发牌、实际出入金；这些不冒充已完成能力。
    12.3 完整状态流程
    开桌检查 → 待开手 → 系统下盲注 → 手工录入底牌 → 核对确认 → 翻前行动 → 烧牌确认与录入翻牌 → 翻牌行动 → 烧牌确认与录入转牌 → 转牌行动 → 烧牌确认与录入河牌 → 河牌行动 → 系统计算 → 荷官确认结算 → 归档 → 下一手／关桌。 | 阶段 | 荷官操作 | 系统校验与玩家展示 | | --- | --- | --- | | 开桌 | 选桌、人数，确认牌具／座位／设备 | 一人一桌；显示规则与模拟带入；已有负责荷官不能抢占 | | 开手 | 点击开始本手 | 至少两名有筹码玩家，系统轮转庄位、下盲注、生成唯一手牌编号（真人桌 T + 8 位 Demo 日期 + 4 码，如 T202505310001；电子桌 H 开头） | | 录底牌 | 按庄位左侧起逐轮录入，按当前目标座位提示点击牌面 | 共 2×参与人数；重复牌禁选，未满不能确认；确认前可撤销最后一张 | | 确认发牌 | 核对本批实际牌面，再点击确认 | 已确认牌不可由荷官改写；保留确认事件；此时才开启玩家行动倒数 | | 玩家行动 | 等待手机事件，查看行动人与动作后确认 | 按行动序、合法金额、最小加注、全押资格校验；收到后停止玩家倒数，等待确认 | | 后续开牌 | 先确认现场烧牌，再录入 3／1／1 张公共牌 | 仅当本街行动结束才开放；不录烧牌面，不允许超量或重复；全押无人可行动时逐街继续录牌 | | 摊牌／计算 | 核对自动生成的结果 | 系统比牌与分池；全部弃牌只剩一人则不补开剩余公共牌，直接计算 | | 结算确认 | 确认无误；有疑问点击暂停 | 金额守恒校验通过才确认，重复请求不重复派发；总后台产生记录 | | 关桌 | 本手已结算／已终止或尚未开手时关桌 | 未完成手牌不能直接关桌；余额仅为本桌模拟筹码 |
    12.4 行动倒数与暂停同步
    本轮行动倒数预设 20 秒，是独立 Demo 参数；不更改电子 WAP 的原倒数。两侧都由同一截止时间计算，不分别减秒。玩家行动经服务端校验并成功提交后立即生效；系统推进下一位玩家并启动其倒数。荷官无需确认玩家行动，只确认牌面与系统结算结果。超时由系统自动处理：可过牌则过牌，否则弃牌。 暂停按钮固定在工作台右上角。点击立即冻结倒数、禁用所有发牌／下注／结算／开下一手动作，再填写报告，不因报告尚未写完继续计时。保存原阶段、玩家、余秒、底池、牌面、已生效行动和日志；暂停期间禁止行动、不推进倒数。恢复时从冻结余秒继续；已生效行动不重给下注机会。刷新读取相同存档与截止时间，页面后台停留不让本地计时漂移。 玩家提示（正式接 WAP 时使用；本轮仅在手机模拟区展示）： > 此牌局异常暂停中，请稍等。工作人员正在核查，您的筹码与已提交行动已保留，暂停期间不计算行动时间。 显示事件编号；不要展示他人底牌、证据、作弊推测、主管内部备注或承诺预计恢复时间。终止提示：本手已终止，相关投入正按处理结果退回；成功退回后才显示“已退回”。
    12.5 错牌、掉牌与争议处理
    | 类型 | 荷官第一步 | 上报必查 | 主管处理原则 | | --- | --- | --- | --- | | 未确认录入误点 | 撤销当前批次的最后一张并重录 | 尚未确认且未向玩家发布 | 不算实体错发；不覆盖已确认记录 | | 已确认牌面与实体不符 | 立即暂停，不自行改牌 | 位置、原录入、真实牌、录像时间、已暴露对象、是否后续行动 | 纯录入错误且没有后续行动可有痕更正；已产生后续行动禁止直接改写，由主管核查 | | 发错对象、提前开牌、掉牌或暴露 | 暂停，保留牌与现场，不擅自洗牌／收回重发 | 牌是否可识别、正反面、谁看到、是否混入弃牌、发生街次、此前行动 | 依具体场况和采用规则裁定；不能所有掉牌都自动作废重发 | | 玩家争议 | 暂停，保留手机行动序与原始事件 | 玩家ID、争议动作、时间、金额、事件ID、录像 | 核对电子事件与现场证据，不凭荷官口述改下注 | | 设备／网络 | 暂停并上报 | 最近确认序号、离线时段、设备、重试结果 | 正式版服务端恢复完整快照，未核对前不能继续发牌 | 报告字段：事件编号、手牌编号、桌号、荷官、阶段、发生／上报时间、异常类型、涉及座位、是否暴露、事实说明、证据引用。系统自动附现场快照、余秒与已生效行动。事实说明必填，证据可先注明未提供，但不得因此自动结案。 状态：立即暂停／待补报告 → 待主管处理 → 恢复待确认或终止待确认 → 荷官执行 → 已恢复或已终止。仍需深入调查的，由风控关联案件继续处理，桌面恢复不等于风控案件结案。 Demo 的主管可选择：①核查无误恢复原状态；②更正纯录入错误后恢复（已产生后续已生效行动时禁止直接更正）；③终止本手并按开手筹码快照退回模拟投入。第三种只是演示处理路径，不宣称所有真实争议都应全额退款。主管原因必填，记录旧值新值与独立操作者；荷官再次确认执行，重复点击不重复退款。

    12.7 参考与适用边界
    - PokerStars Live《Cash Game Rules》“Decision-making procedures”：异常及时通知工作人员，现场主管作裁定。参考其升级处理职责，不复制其现场行为限制。[官方来源](https://www.pokerstarslive.com/poker/cashgamerules/) - PokerStars Live《Tournament Poker Rules》说明遵循 TDA，且对现场手机使用有额外限制；本产品的“手机电子下注＋真人录牌”是产品自定义混合流程，并非该竞品原有操作模式。[官方来源](https://www.pokerstarslive.com/poker/rules/) - TDA 官方规则入口说明建议程序需要结合具体场况判断；本方案不把异常类别直接等同于自动退款或重发。[官方来源](https://www.pokertda.com/poker-tda-rules/) 以上为公开规则研究，不声称取得竞品内部荷官控制台设计。暂停弹层、同源计时、报告快照和双角色确认是基于研究提出并在本地 Demo 实现的产品方案。

    后台 · 三套后台架构与逐页筛选

    规格 · 排入 I1～I5 迭代开发与验收。

    共用列表与筛选行为

    - 总后台通用范围：商户、站点；代理按登录身份锁定本站或自己俱乐部，不能通过改参数扩大范围。详情、搜索建议、合计、待办数、导出使用同一范围。

    - 下表每行是一页或独立页签；列出的字段必须提供具名筛选控件，不能用“任意栏位筛选”代替。ID/单号精确查询，名称关键词模糊查询，枚举下拉，数值上下限，日期起止。关联选项联动，切换上级清除无效下级。

    - 记录页默认近 30 天；仪表盘默认今天、可选近 7/14/30 天；周结默认上个完整自然周，商户月结默认当月预估；配置页默认全部有效配置，业务列表默认全部状态，牌桌默认进行中。日期字段在控件上标明创建、发生、审核或结算，多个日期同时设置按 AND 处理。

    - 日期依站点时区显示，结束日期包含当天，接口用次日零时作排他上界；跨站汇总明确显示统一查询时区。不同本位币分组汇总，不直接相加；换算报表须显示币种、汇率时间和口径。

    - 查询、重置、收合高级筛选；重置不清除身份范围。金额最小值不得大于最大值，起日不得晚于迄日，非法条件不发请求。精确单号未命中时提示检查日期范围。

    - 筛选或每页条数变化回第 1 页，保留排序；默认时间倒序，同时间按 ID 稳定排序。每页 50/100/200，显示总数；详情返回恢复筛选与页码。并发查询只呈现最后一次结果。

    - 汇总针对全部筛选结果，不只当前页；CSV 导出同筛选、同排序、同权限，注明时区币种，不导出隐藏敏感字段。大批量采用导出任务并记录日志。

    - 加载、无数据、筛选无结果、无权限、模块未开通、请求失败分别展示。配置编辑页没有列表筛选时，用对象ID与配置版本定位；保存展示改前改后，审批后生效。

    11.4 代理后台架构与权限

### 13.2 两层分成与设置细则

采用待业务验收的计算默认：赛事服务费与现金桌抽水分别计算，比例均基于同一有效收入基数。平台给总代比例 P，总代给直属一级代理比例 C，要求 0 ≤ C ≤ P ≤ 100%；不得把 C 再乘 P。直属一级代理归属收入 B：代理池=B×P，一级代理=B×C，总代留存=代理池−一级代理。例：B=100、P=30%、C=10%，一级代理10、总代20、平台代理池外70；总代直属成员收入无下级分成。各来源分别核算，禁止两层重复全额领取。

设置字段：代理与俱乐部、来源类型、平台比例上限、申请比例、结算币种、周期、生效时间、申请人、审核人、修改理由、版本、状态。总代只能提交直属一级代理比例申请，一级代理只读；平台审批后下一完整结算周期生效，申请人与审核人分离。平台降低 P 时必须同步验证所有 C，存在超限则阻止生效。费率与成员归属按收入发生时的有效版本留快照，变更不得重算已结历史；追回用关联原账单的调整单，禁止删账。使用最小货币单位计算，先算代理池与下级，再以差额计算总代，保留舍入规则与币种，不混币合计。

已结算且归属明确的记录才计入；取消、终止、退回筹码、未结手牌不算收入；抽水和赛事服务费去重。负调整结转与争议金额暂缓须显示来源和理由。沿用周一结算并入账（R39-UI-01）；实际接口实现仍待开发。

总代查询范围明确区分「我的俱乐部」与「直属一级代理俱乐部（获授权）」；默认自己的范围。上级关系本身不授予下级俱乐部成员编辑、审核、消息发送或隐藏底牌访问权。一级代理只查自己的及明确授权管理的俱乐部，不能查总代或兄弟代理。每条俱乐部数据绑定 club_id 和创建者／代理归属，成员可加入多个俱乐部，但不得因此将其其他俱乐部记录一并返回。总后台可按总代、一级代理、俱乐部逐层筛选，全部查询、导出、统计和深链使用同一权限范围。

验收至少准备总代自建俱乐部、一级代理自建俱乐部、兄弟代理俱乐部及多俱乐部成员四组数据，验证列表、详情、待审角标、收入和分成一致；无俱乐部空态、切换范围、跨俱乐部ID访问与导出均需测试。当前 Demo 尚未完成上述查询，不得标为已开通。
